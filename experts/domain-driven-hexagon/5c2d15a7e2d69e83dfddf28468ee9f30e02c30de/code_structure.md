## Module and Package Organization

The codebase uses two parallel organizational dimensions:

**1. By layer** (within `src/libs/`) — generic, reusable infrastructure code organized by architectural concern:
- `ddd/` — DDD building blocks (pure TypeScript, no framework coupling)
- `db/` — SQL repository base class
- `api/` — HTTP response/error types
- `application/` — NestJS interceptors and request context
- `exceptions/` — typed exception hierarchy
- `decorators/` — `@frozen`, `@final` class decorators
- `types/` — TypeScript utility types
- `ports/` — shared port interfaces (e.g., `LoggerPort`)

**2. By feature module** (within `src/modules/`) — each bounded context gets its own self-contained folder. Within a module, code is organized by CQRS use-case using **Vertical Slice** structure: `commands/<use-case>/`, `queries/<use-case>/`.

## Code Organization Patterns

1. **Vertical Slices for commands** — each command has its own folder containing the command, service, DTO, and all controllers (HTTP/CLI/message/GraphQL). This keeps all related code co-located.

2. **Ports and Adapters** — the domain layer never imports from infrastructure. Repositories are accessed through port interfaces (`UserRepositoryPort`), with concrete implementations injected via NestJS DI tokens.

3. **DI Tokens** — each module defines string tokens (`USER_REPOSITORY`, `WALLET_REPOSITORY`) in `*.di-tokens.ts` files to decouple injection points from concrete classes.

4. **Barrel exports** — `index.ts` files at each `libs` sub-folder enable clean cross-lib imports like `import { Entity } from '@libs/ddd'`.

5. **Path aliases** — `tsconfig.json` defines `@libs/*`, `@modules/*`, `@src/*`, `@config/*`, `@tests/*` aliases to avoid relative path spaghetti.
