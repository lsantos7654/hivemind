## Module and Package Organization

The source is organized as a single TypeScript package with clear separation of concerns:

### Public API layer (`src/marked.ts`)
Creates a default `Marked` instance and re-exports all public symbols. Acts as the stable public surface area. The top-level `marked(src)` function is a convenience wrapper around `markedInstance.parse(src)`.

### Core orchestration (`src/Instance.ts`)
The `Marked` class owns the mutable `defaults` object and implements:
- `use(...extensions)` — merges extensions into defaults with fallback-chain wrapping
- `parse(src, options)` — full pipeline execution (sync or async via `async` flag)
- `parseInline(src, options)` — inline-only pipeline
- `walkTokens(tokens, callback)` — recursive token tree traversal
- `setOptions(opt)` — shallow-merge options update

### Lexer/Tokenizer split (`src/Lexer.ts` + `src/Tokenizer.ts`)
`_Lexer` owns the overall tokenization loop (block → inline queue drain), while `_Tokenizer` contains one method per token type. This split allows tokenizer methods to be overridden individually via `marked.use({ tokenizer })` without replacing the entire lexer loop.

### Parser/Renderer split (`src/Parser.ts` + `src/Renderer.ts`)
`_Parser` owns the dispatch loop (switch on `token.type`), while `_Renderer` contains one method per token type. Overridable individually via `marked.use({ renderer })`.

### Type definitions (`src/Tokens.ts`, `src/MarkedOptions.ts`)
All token shapes are defined as TypeScript interfaces in the `Tokens` namespace. Option and extension interfaces are in `MarkedOptions.ts`. These are bundled into `lib/marked.d.ts` by `dts-bundle-generator`.

## Key Files and Their Roles

| File | Purpose |
|------|---------|
| `src/marked.ts` | Entry point; singleton + all public re-exports |
| `src/Instance.ts` | `Marked` class; `use()`, `parse()`, `walkTokens()` |
| `src/Lexer.ts` | Tokenization loop; manages inline queue; `blockTokens()`, `inlineTokens()` |
| `src/Tokenizer.ts` | Per-token regex matching; 20+ methods (fences, heading, list, emStrong, etc.) |
| `src/Parser.ts` | Token dispatch loop; calls renderer methods; `parse()`, `parseInline()` |
| `src/Renderer.ts` | HTML generation; one method per token type (15 block + 8 inline) |
| `src/TextRenderer.ts` | Strips HTML; used for `alt` text and plain-text output |
| `src/Hooks.ts` | Pipeline lifecycle: `preprocess`, `processAllTokens`, `postprocess`, `emStrongMask`, `provideLexer`, `provideParser` |
| `src/MarkedOptions.ts` | `MarkedOptions`, `MarkedExtension`, `TokenizerExtension`, `RendererExtension` types |
| `src/Tokens.ts` | All token type interfaces (`Tokens.Heading`, `Tokens.List`, `Tokens.Code`, etc.) |
| `src/defaults.ts` | `_getDefaults()` factory; global `_defaults` singleton |
| `src/rules.ts` | Regex rule sets: `block.normal`, `block.gfm`, `block.pedantic`, `inline.normal`, `inline.gfm`, `inline.breaks`, `inline.pedantic` |
| `src/helpers.ts` | `cleanUrl()` — sanitizes link hrefs; `escapeHtmlEntities()` — HTML entity escaping |
| `esbuild.config.js` | Builds `lib/marked.esm.js` and `lib/marked.umd.js` from `src/marked.ts` |

## Code Organization Patterns

**Naming convention**: Internal/implementation classes are prefixed with `_` (e.g., `_Lexer`, `_Renderer`) and exported under both the prefixed and non-prefixed name. The public-facing aliases (e.g., `Lexer`, `Renderer`) are the ones users interact with directly.

**Fallback chain pattern**: When multiple extensions override the same renderer/tokenizer/hook method, each wraps the previous. Returning `false` from an override triggers the fallback to the prior implementation, enabling composed extension stacks.

**Generic type parameters**: `Marked<ParserOutput, RendererOutput>` supports non-string output types. The default `string` type satisfies normal usage, but extensions can produce DOM nodes, React elements, or other types.

**Static factory methods**: `_Lexer.lex()`, `_Lexer.lexInline()`, `_Parser.parse()`, and `_Parser.parseInline()` are static convenience wrappers over constructing instances, used internally and accessible publicly.

**Inline queue pattern**: Block tokenization queues inline content via `lexer.inline(text, tokens)` rather than processing immediately, since inline tokenization must happen after all block tokens are known. The queue is drained at the end of `_Lexer.lex()`.
